# 演进路线

## 目标架构

长期目标是让兼容协议与上游 Provider 独立演进：外部协议只依赖稳定的内部请求、事件、模型和错误契约；Provider 负责 Gemini Web 的私有实现；账号与认证作为横切基础设施提供能力。

## 建议阶段

1. 使用 RPC、模型、流式、取消和错误 fixture 固化当前行为。
2. 稳定通用的请求、事件、模型和错误契约。
3. 将模型解析、账号选择、Provider 调用和重试归入应用服务。
4. 拆分 HTTP schema、请求 mapper、事件 encoder 和错误映射。
5. 为更多 Provider 泛化账号、模型注册和能力声明。
6. 建立契约测试、可观测性指标和兼容性回归门禁。

## 设计约束

不要在私有 Web RPC、Cookie 字段或 session ID 的契约尚未明确前过度抽象。优先抽象稳定边界，保留 Provider 内部对上游变化的隔离空间。

任何涉及流式输出、认证恢复或重试的改动，都必须先说明副作用边界：请求是否已被上游接受、下游是否已收到内容、账号租约是否已释放，以及重连是否会重复提交。
